# Mistral Vibe réglé pour Devstral 2

Configuration prête pour [Mistral Vibe](https://github.com/mistralai/mistral-vibe) (l'assistant de code en ligne de commande de Mistral) avec le modèle **Devstral 2** (`devstral-2512`, « Devstral Medium 2512 »).
Vérifiée avec mistral-vibe **3.0.1**.

## Installation en 3 étapes (Windows)

1. **Récupérer le dépôt** (Git Bash) :
   ```bash
   git clone https://github.com/RomainC-lab/vibe-devstral.git
   cd vibe-devstral
   ```
2. **Lancer l'installation** (installe Vibe avec pip et copie les réglages dans `~/.vibe/`) :
   ```bash
   bash installer.sh
   ```
   ou dans PowerShell : `powershell -ExecutionPolicy Bypass -File .\installer.ps1`
   Rien n'est écrasé : si tu as déjà un fichier différent, il est gardé et listé à la fin.
   Pour le remplacer quand même : `bash installer.sh --force` (l'ancien est copié dans `~/.vibe/sauvegarde-<date>/`).
3. **Mettre ta clé** dans `~/.vibe/.env` (c'est-à-dire `C:\Users\<toi>\.vibe\.env`), créé par l'installation :
   ```
   MISTRAL_API_KEY=ta_cle
   ```
   Puis, dans le dossier d'un projet : `vibe`

La clé ne va **jamais** dans ce dépôt ni dans un projet : seulement dans `~/.vibe/.env`.
Si `vibe` est introuvable après l'installation, l'installeur affiche le dossier à ajouter au PATH Windows.

## Accès par l'API Mistral ou par le serveur de l'entreprise

Le fichier `~/.vibe/config.toml` prévoit les deux :

- **API Mistral** (par défaut) : modèle `devstral`, clé `MISTRAL_API_KEY`.
- **Serveur de l'entreprise** (compatible OpenAI, par ex. vLLM) : dans `~/.vibe/config.toml` sur ton PC,
  1. remplace `https://ADRESSE-DU-SERVEUR/v1` par la vraie adresse ;
  2. vérifie le nom du modèle (`name = ...`) : c'est celui que donne `<adresse>/v1/models` ;
  3. mets la clé dans `~/.vibe/.env` (`ENTREPRISE_API_KEY=...`), ou `api_key_env_var = ""` s'il n'y en a pas ;
  4. `active_model = "devstral-entreprise"` est déjà le choix par défaut (pour l'API Mistral : `/model` puis `devstral`).

Ne fais ces changements que dans `~/.vibe/config.toml`, jamais dans ce dépôt : pas d'adresse de serveur sur GitHub.
Derrière un proxy d'entreprise, `enable_system_trust_store = true` (déjà mis) fait accepter les certificats installés dans Windows.

## Ce qui est réglé

- **Modèle** : température 0,15 (celle de la fiche officielle de Devstral 2), pas de mode « réflexion », fenêtre de 256k jetons, résumé automatique de la conversation à 160k jetons pour garder des réponses précises.
- **Mode de départ** : `accept-edits` : Vibe modifie les fichiers sans demander, mais demande avant chaque commande shell (sauf lectures comme `git status`, `git diff`, `ls`).
- **Sécurité** : écriture interdite dans `.env`, `*.pem`, `*.key`, `*.pfx`, clés SSH ; lecture d'un `.env` toujours soumise à ton accord.
- **Confidentialité** : statistiques d'usage coupées, pas de signature « Generated by Mistral Vibe » dans les commits, pas de mise à jour automatique.
- **Consignes** (`~/.vibe/AGENTS.md`) : réponses en français, plan avant un gros changement, tests avant de dire « fini », petits changements, pas de secrets, question en cas de doute.

## Les commandes ajoutées (skills)

Tape `/` dans Vibe pour les voir :

- `/planifier` : explore le code et propose un plan, sans rien modifier. À faire avant une vraie fonctionnalité.
- `/relire-diff` : relit tes changements en cours (`git diff`) et liste les problèmes, du plus grave au moins grave.
- `/ecrire-tests` : écrit des tests au style du projet et les lance.
- `/preparer-commit` : vérifie le diff (secrets, fichiers en trop, tests) et propose le message de commit. Ne commite qu'avec ton accord, ne pousse jamais.
- `/creer-agents-md` : explore le projet et écrit son `AGENTS.md` (commandes, dossiers, règles). Relis-le ensuite.
- `/retenir <la chose>` : note une consigne ou un piège dans l'`AGENTS.md` pour qu'il s'en souvienne aux prochaines sessions. Il le fait aussi tout seul quand tu le corriges.

Vibe peut aussi lancer tout seul `planifier`, `relire-diff` et `ecrire-tests` quand ça colle à ta demande.

## La doc de tes outils (skills d'outils)

Vibe n'a pas internet et le MCP est interdit au travail : ces skills lui donnent la doc de **tes versions**. Il les ouvre tout seul quand ta demande en parle (tu peux aussi taper `/netbox`, `/aap`…). Chacune a un `SKILL.md` court et des fichiers `references/` qu'il ne lit que si besoin.

- `/netbox` : **NetBox 4.0.11** : API REST (filtres, pagination, brief/fields), pynetbox 7.4.1, scripts personnalisés, custom fields, GraphQL, plugins, ce qui a changé en 4.0 et ce qui n'existe pas encore.
- `/aap` : **AAP 2.4** (ton « 4.5.24 » est la version de l'*automation controller*, livrée avec AAP 2.4) : job templates, surveys, credentials, inventaires, execution environments, API `/api/v2/`, collections `ansible.controller` / `awx.awx`, ce qui n'arrive qu'en AAP 2.5.
- `/ansible` : **ansible-core 2.17** : FQCN, bonnes pratiques, pièges Jinja, ansible-lint, collection `netbox.netbox` (modules, `nb_lookup`, inventaire `nb_inventory`), ce qui a changé en 2.17 et ce qui vient après.
- `/python-311` : **Python 3.11** : le code du travail doit tourner en 3.11 même si Vibe tourne en 3.12 sur ton PC ; liste de ce qui est interdit (3.12 et plus) avec le remplacement, et comment vérifier.

Tout a été vérifié dans la doc officielle de chaque version, mais relis ce qui compte : une skill peut se tromper.

### Écrire une nouvelle skill d'outil avec le modèle

1. Copie `modeles/skill-outil/` dans `vibe/skills/<nom-de-l-outil>/` (minuscules, chiffres et tirets ; le même nom que la ligne `name:`).
2. Remplis `SKILL.md` : la `description` (ce que c'est, la version, « À utiliser quand… » avec les mots que tu tapes), la version, les changements, l'usage courant, les pièges, ce qui n'existe **pas** dans ta version, et quand ouvrir chaque fichier de référence. Moins de ~150 lignes.
3. Mets les longs détails dans `references/<sujet>.md` (un fichier par sujet, voir `references/exemple-sujet.md`) et cite-les dans `SKILL.md`.
4. Rien de privé : pas de nom de serveur, d'adresse, d'identifiant ni de mot de passe.
5. Installe (`bash installer.sh`, ou copie le dossier dans `~/.vibe/skills/`), relance `vibe` et tape `/<nom-de-l-outil>` pour l'essayer.

**Sous-agent `relecteur`** : un relecteur en lecture seule, avec un contexte neuf. Demande par exemple : « fais relire mes changements par le relecteur ».

## Pour chaque projet

Lance `/creer-agents-md` dans le projet, ou copie `modeles/AGENTS.md` à la racine sous le nom `AGENTS.md` et remplis-le (commandes de test, dossiers, règles). Vibe le lit à chaque session : c'est ce qui l'aide le plus.

## Astuces

- **Shift+Tab** : change de mode (`ask` = demande tout, `accept-edits`, `auto-approve` = ne demande rien, à éviter sur du code important).
- **@fichier** : cite un fichier dans ta demande (`@src/main.py`), avec autocomplétion.
- **!commande** : lance une commande toi-même sans passer par l'IA (`!git status`).
- **Relecture à froid** : après un gros changement, ouvre une nouvelle session (`/clear` ou relance `vibe`) et fais `/relire-diff` : un regard neuf trouve plus de problèmes.
- **Longue session** : `/compact` résume la conversation à la main ; `vibe -c` reprend la dernière session.
- **Ctrl+J** : nouvelle ligne dans ta demande ; **Échap** : interrompt Vibe.
- Mise à jour de Vibe : `py -m pip install -U mistral-vibe`. Mise à jour de ces réglages : `git pull` puis `bash installer.sh` (ajoute les nouveaux fichiers sans toucher aux tiens) ou `bash installer.sh --force` (remplace, avec sauvegarde).

## Contenu du dépôt

```

vibe/AGENTS.md                 consignes pour tous les projets
vibe/skills/*/SKILL.md         les 6 commandes et les 4 skills d'outils ci-dessus
vibe/skills/*/references/      la doc détaillée des skills d'outils
modeles/skill-outil/           modèle pour écrire une nouvelle skill d'outil
vibe/agents/relecteur.toml     le sous-agent relecteur
modeles/AGENTS.md              modèle d'AGENTS.md pour un projet
vibe-env.exemple               modèle du fichier des clés
installer.sh / installer.ps1   installation (Git Bash / PowerShell)
```
